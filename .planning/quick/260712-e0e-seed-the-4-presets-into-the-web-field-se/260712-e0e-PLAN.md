<objective>
Make the web app usable out of the box: ship the 4 presets into the field-set store on
startup, land the Upload screen with a field set already chosen, and make the
"Upload & Map" button honest — disabled with a reason when it cannot act, instead of
enabled and silently doing nothing.

Purpose: three verified defects compound into one dead end. `presets/` ships 4 field
sets but they are reachable only from the CLI's `--fields presets/assay-potency.yaml`
(`cli.py:712`); `GET /api/field-sets` on the live server returns two user rows, one of
them empty-named. So a web curator lands on Upload with an effectively blank required
dropdown (`Upload.tsx` initialises `selectedTemplateId` to `null` and never defaults
it), clicks the enabled-looking "Upload & Map" button, and `Upload.tsx:147`'s
`!selectedTemplate` early-return swallows the click with no error and no hint. Nothing
happens. That is the bug the user reported.

Output: one new preset-resolution module, one new seeding module, a lifespan wire in
`app.py`, one new pure frontend selection module, edits to `Upload.tsx` and
`UploadDropzone.tsx`, two new test files, and a rebuilt `frontend/dist`.
</objective>

re-deriving them:

- `fields.loader.load(path) -> FieldSet` is the single YAML/JSON field-set entry point
  (safe_load only, D-03). `tests/test_presets.py` already proves all 4 presets load
  through this identical call. Reuse it; write no second loader.
- `FieldSet` is a frozen dataclass with `.name` (`str | None`), `.fields`, `.signature`,
  `.to_dict()`. All 4 preset YAMLs declare a top-level `name:` (`assay-potency`,
  `clinical-labs`, `pk-parameters`, `reagent-inventory`).
- Presets live at repo-root `presets/*.yaml` in a checkout, and at
  `assayingest/presets/` inside the built wheel (`pyproject.toml`
  `[tool.hatch.build.targets.wheel.force-include]`, line 39-40). Resolution must handle
  BOTH; do not assume the process CWD is the repo root.
- `FieldSetTemplateStore` (abstract) exposes exactly three methods: `save(name,
  field_set) -> id`, `get(id) -> FieldSet | None`, `list() -> list[tuple[id, name]]`.
- `SqliteFieldSetStore.save` UPSERTS on `UNIQUE(name)` and mints a **new uuid4 id on
  every save** (`ON CONFLICT(name) DO UPDATE SET id=excluded.id`). Calling `save` on
  every startup would therefore churn the template id on each restart — breaking the
  localStorage last-used id from Task 2. Seeding MUST be insert-if-absent: read
  `store.list()`, skip any name already present.
- `api/deps.py::get_field_set_store()` is the DI seam. Tests override it with
  `app.dependency_overrides[get_field_set_store] = lambda: store` (see
  `tests/api/test_field_sets.py:98`).
- `app.py` currently has NO lifespan/startup handler. No existing test constructs the
  client as `with TestClient(app)` (verified by grep) — every one uses bare
  `TestClient(app)`, which does not run lifespan. So adding a lifespan cannot make an
  existing test write to the real `.assayingest/profiles.db`.
- `frontend/vite.config.ts` sets `test.environment: 'node'` — there is no jsdom and no
  @testing-library/react. Frontend tests in this repo are pure-logic tests over
  `src/state/*.ts` (`state/upload.test.ts`, `state/fieldSet.test.ts`). Do NOT add DOM
  test infrastructure; put the new logic in a pure module and test that.
- `FieldSetTemplate` (`frontend/src/lib/types.ts:37`) = `{ id: string; name: string;
  field_set: FieldSetPayload }`.
- `UploadDropzone` has exactly ONE call site: `frontend/src/screens/Upload.tsx:251`.
- `frontend/dist` is **gitignored** (`frontend/.gitignore:11`). Rebuild it, but never
  `git add -f` it.
- Non-negotiable contract: `routes/upload.py::_resolve_field_set` (line 298) must keep
  raising 422 when neither `field_set` nor `field_set_template_id` is supplied. This
  plan changes what is AVAILABLE, not the API contract. Do not touch `upload.py`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo `presets/*.yaml` -> server process | Shipped, version-controlled data, loaded at startup. Trusted-ish: it is repo content, but it is still YAML fed to a parser. |
| existing SQLite rows -> seeding logic | The live DB already holds curator-authored rows (including an empty-named one). Seeding must not destroy them. |
| browser localStorage -> Upload screen | A stale/attacker-set template id is client-side untrusted input to the picker. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-e0e-01 | Elevation of Privilege | `fields/presets.py` YAML load | medium | mitigate | Load exclusively through `fields.loader.load`, which is `yaml.safe_load`-only (D-03/T-02-01). No new parser, no `yaml.load`. |
| T-e0e-02 | Tampering | `learning/seed.py` vs existing rows | high | mitigate | Insert-if-absent (skip any name already in `store.list()`), never `save`-as-upsert. A curator's own template — including one named after a preset — is never overwritten or re-id'd. Task 1's test asserts this explicitly. |
| T-e0e-03 | Denial of Service | app lifespan | medium | mitigate | Seeding is wrapped so a missing/corrupt presets directory logs a consequence-shaped warning and the server still starts and serves `/api/*`. |
| T-e0e-04 | Tampering | localStorage last-used template id | low | mitigate | `pickDefaultTemplateId` only accepts a stored id that is present in the server-returned template list; a stale or forged id falls back to the first template. The id is never sent to the server unresolved — the server still gets a full `field_set` payload and still enforces its own 422 gate. |
| T-e0e-05 | Spoofing | `_resolve_field_set` contract | low | accept | Unchanged by this plan. Seeding alters availability, not the API contract; `upload.py` is not in `files_modified`. |

No package-manager installs in this plan (no npm/pip/cargo `install` step) — the package
legitimacy gate does not apply.
