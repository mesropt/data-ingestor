<objective>
Make the signup handler fail *clean*: if minting the email-verification token raises,
nothing is written to the user store, so the account does not exist and the user can
simply retry.

Purpose: today `signup()` calls `store.save(user)` and only then
`create_verification_token(user.id)`. That token call raises `RuntimeError` when
`SESSION_SECRET` is unset. The observed production failure: the row was persisted, the
token step raised, FastAPI returned an unhandled 500, the SPA said "We couldn't create
your account right now" — and the account was left in the DB **unverifiable** (no link
was ever emitted) and **un-retryable** (a second attempt hits the 409 "already
registered"). Reordering the two steps turns a corrupting failure into a no-op failure.

Output: one new failing-then-passing test in `tests/api/test_auth_routes.py`, and a
two-line reorder (plus corrected comment) in `src/assayingest/api/routes/auth.py`.
</objective>

- `src/assayingest/auth/tokens.py`
  - `create_verification_token(user_id: str) -> str` — builds a `URLSafeTimedSerializer`
    from `os.environ["SESSION_SECRET"]` and returns `.dumps({"user_id": user_id})`.
    It performs **no store lookup and no I/O**; its only input is the string `user_id`.
    It raises `RuntimeError("SESSION_SECRET is not set; cannot mint verification tokens. ...")`
    when the env var is missing/empty.
  - => Calling it before `store.save(user)` is safe: `user.id` is an in-memory
    `str(uuid.uuid4())` generated in the handler itself.

- `src/assayingest/api/routes/auth.py`
  - `signup()` currently: 409-check -> build `User` -> `store.save(user)` ->
    `token = create_verification_token(user.id)` -> build `verify_url` -> `logger.info(...)`
    -> return `SignUpAcceptedOut`.
  - The route imports the function by name
    (`from ...auth.tokens import create_verification_token`), so a test that patches it
    must patch the name on the **route module** (`assayingest.api.routes.auth`), not on
    `assayingest.auth.tokens`.

- `src/assayingest/auth/store.py` — `UserStore.save/get/get_by_email/mark_verified/get_or_create_by_email`.

- `tests/api/test_auth_routes.py`
  - `_client(tmp_path, monkeypatch) -> tuple[TestClient, SqliteUserStore]` — sets
    `SESSION_SECRET`, clears the Google flag, overrides `get_user_store` with a tmp-path
    `SqliteUserStore`, returns `(TestClient(app), store)`.
  - `_clear()` — clears `app.dependency_overrides`.
  - Default `TestClient` re-raises server-side exceptions, so an unhandled `RuntimeError`
    from the handler surfaces to the caller as a raised `RuntimeError` (usable with

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous client → POST /api/auth/signup | Untrusted email/password crosses here; the handler writes a user row and mints a signed token |
| server process → user store (SQLite) | The only place a signup persists state; must not be written on a partially-failed signup |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-c47-01 | Denial of Service | `signup()` in `api/routes/auth.py` | medium | mitigate | A token-mint failure currently persists an account that can never be verified and can never be re-created (the 409 blocks retry) — a permanent self-DoS on that email address. Task 2 reorders the mint before the save so a failure writes nothing and the email stays claimable. |
| T-c47-02 | Information Disclosure | signup failure path | low | accept | The `RuntimeError` propagates to an unhandled FastAPI 500. It names a server config gap (`SESSION_SECRET is not set`), not user data or a secret value. Suppressing the trace at the HTTP boundary is a separate concern (see `<follow_ups>`); this plan does not change error surfacing. |
| T-c47-03 | Tampering | verification token | low | accept | Unchanged by this plan. The token stays a stateless, salt-isolated itsdangerous payload carrying only `user_id`; minting it earlier does not weaken its signature, salt, or 24h max_age. |
</threat_model>

<follow_ups>
Deliberately OUT OF SCOPE for this plan (do not implement here; capture for later triage):

1. **Startup validation of `SESSION_SECRET`.** The app boots happily without it and only
   explodes at the first signup. A fail-fast check at app startup would turn a runtime 500
   into an un-missable boot error. Worth doing — but it is a different change with a
   different blast radius.
2. **A 500-handling boundary for auth routes.** The SPA currently shows a generic
   "We couldn't create your account right now" for an unhandled 500. Mapping the
   config-error `RuntimeError` to a deliberate 503 with an operator-facing detail would be
   an improvement.
3. **Frontend retry affordance.** No frontend change is made here; after this fix the
   existing SPA retry path already works, because the email is no longer taken.
</follow_ups>
