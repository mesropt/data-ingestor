<objective>
Fix silent data loss in the live CSV parser. `delimiter.py::_read_or_name_the_failure` passes `comment="#"` to `pd.read_csv(engine="python")`, and that kwarg truncates the rest of ANY line from the first `#` found anywhere in it — including a header row that is not a comment at all.

`data/synthetic/helixbio_export.csv` has a `# Reps` header column. Its header row is truncated to 4 names while every data row still carries 6 fields, so pandas treats the first data column as an unnamed index. Verified reproduction:

- `parse(...).headers` → `['Compound Name', 'Endpoint', 'Conc (uM)', 'Gene Symbol', '']`
- `parse(...).rows[0]` → `['EC50', '0.045', 'EGFR', '3', '03/11/2025']` — `HLX-100` is gone from every row.

Every column shifts one position left and the compound identifier is destroyed. Downstream, Claude maps a corrupted table and the human cannot clear it from Review. This is the project's cardinal sin — silent data loss on a life-sciences file — and it fires on the live `/api/upload` path (`parse()`), though not on the legacy `parse_file()`.

Purpose: restore the parser's honesty. Comment stripping must remove WHOLE comment lines only, never truncate a line mid-way, while still stripping the leading `#` metadata block that would otherwise poison delimiter sniffing.
Output: a corrected `delimiter.py` plus regression tests that fail today and pass after the fix.
</objective>

<decision_record>
**D-01 — A `#`-prefixed line that is structurally a header/data row is REFUSED, not dropped.**

The one genuinely ambiguous case is a file whose header row itself begins with `#` (e.g. `# ID,Value,Target`). Two options:

- (a) Treat it as a comment and drop it. The first data row then silently becomes the header — a shifted table that looks clean and maps every field wrong. This is the same class of silent corruption we are fixing. **Rejected.**
- (b) **Chosen:** detect it and raise a named `ValueError` naming the consequence and the fix. Fail-closed on ambiguity is the project's stated principle; `read_csv_grid` already raises named `ValueError`s for the other "genuinely broken file" cases (D-05), so this is consistent with its contract and needs no signature change (which the scope fence forbids anyway).

Detection rule: a comment line is prose; a header row is structured. After the grid is parsed, split each dropped line on the resolved delimiter. If it yields **exactly the same field count as the table** and the table has **>1 column**, it is not prose — refuse. Pinnacle's comment lines yield 1 and 4 fields against 7 columns, so the real corpus is unaffected (verified).

A `StructureQuestion` would be more idiomatic than a `ValueError`, but `read_csv_grid` returns a `tuple` and changing its return type would ripple into `table.py`, which the scope fence puts out of bounds. Note this trade-off in the summary.
</decision_record>
