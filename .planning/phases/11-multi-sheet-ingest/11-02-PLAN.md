<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| shipped YAML → crosswalk DB | Preset data becomes governed crosswalk rows with provenance |
| startup seeder → curator-owned Schema | The seeder writes into objects a human may already have edited |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-04 | Tampering | `seed_schema_aliases` vs D-10-15 tombstones | high | mitigate | `seed_alias` checks for ANY row (live or tombstoned) before inserting; a curator-removed starter alias is never resurrected. Pinned by a dedicated test. |
| T-11-05 | Tampering | seeder vs curator's Schema edits | high | mitigate | The seeder only ever inserts aliases; it never calls `add_or_update_fields` / `update_field` / `remove_field` / `remove_alias`. Grep-asserted in acceptance criteria. |
| T-11-06 | Repudiation | alias provenance | medium | mitigate | Seeded aliases carry `provenance_actor="preset-seed"` and a fixed `created_at` constant; `add_alias`/`seed_alias` never restamp an existing row (ALIAS-03) |
| T-11-07 | Tampering | SQL injection via alias spellings | medium | mitigate | Vendor/source_column reach SQL only through parameterised placeholders, reusing `add_alias`'s existing discipline |
| T-11-SC | Tampering | package installs | high | accept | This plan installs ZERO packages (no `uv add`, no `npm install`). If any dependency change is proposed, stop and surface it. |
</threat_model>
