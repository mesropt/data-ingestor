**Gap 1 (INGEST-04):** `service.confirm()` re-validates from scratch but never threads the human's resolved date order through. ## Decision 1 (gap 1): retain the human's ANSWER, re-derive the FORMAT

The obvious fix -- stash `resolution.formats` on `UploadEntry` and pass it to `confirm()` -- is the WRONG one. `confirm()` is the P1 gate; its whole discipline (see its docstring) is "rebuild a FRESH proposal, re-run validate(), never trust a claim the caller carries in." A retained format dict is a claim.

Retain instead the ONE thing the server genuinely cannot re-derive: **the human's per-column order** (`day_first` | `month_first`) -- which is already exactly what `POST /api/date-format/resolve` accepts, and already deliberately NOT a format string (T-10-21, 10-05). `confirm()` then calls `service.resolve_date_formats(table, proposal, field_set, answers=date_answers)` itself, against the RETAINED table and its OWN freshly-rebuilt proposal, and derives the concrete formats server-side -- exactly as `date_format.py` already does.

This is strictly better than retaining formats, and it is the reason to prefer it:

- It re-derives from the table, so it survives the human EDITING a mapping at review time (re-pointing the date field at a different source column) -- a retained format dict would be silently stale and would convert the wrong column's values under the wrong order.
- It also fixes, for free, the *second* half of the gap 10-05 flagged: an **unambiguous-but-undeclared** date column (resolved from its own evidence inside `resolve_or_map`, with no human question ever raised) is TODAY also re-flagged at confirm. With `answers=None`, `resolve_date_formats` still resolves that column deterministically from evidence, so it clears at confirm too.
- The client cannot smuggle a format: `ConfirmRequest` gains NO new field. The answers come from the retained `UploadEntry`, keyed by the `upload_token` the server minted.

**`answers=None` vs `answers={}` -- use `None` when nothing was answered.** 10-03 defined this asymmetry deliberately (see its SUMMARY): `None` means "first pass, never raise"; any non-`None` dict asserts "resolve everything NOW" and raises `UnresolvedDateColumnsError` on a still-ambiguous column. Pass `entry.date_answers` straight through -- it is `None` on every upload that never raised a date question, which keeps today's behavior for those flows byte-identical and introduces no new exception into confirm's contract for them. A genuinely ambiguous, unanswered column still fails closed: `resolve_date_formats` leaves it out of `formats`, `validate()` flags it amber, and confirm's existing `is_ready` check raises `NotReadyError` -> 422. Fail-closed is preserved through the EXISTING gate, not a new one.

`confirm()` must thread `resolution.formats` into **both** `validate(...)` **and** `canonical.assemble(...)`. Only the second one makes the exported cell actually ISO 8601. Threading one and not the other yields a green gate and a wrong file -- the worst possible outcome for a tool whose motto is "trust the numbers".

## Decision 2 (gap 2): allow an EMPTY Schema, via an opt-in on exactly one caller

A Schema with zero canonical fields is a legitimate starting state -- you create it, then populate it with `add_schema_field` (shipped in 10-04). `from_dict`'s "declares no fields" guard was written to protect **field-set uploads** (a curator handing the tool a YAML/JSON template that turns out to be empty is broken input). Schema *creation* is a different entry point with a different meaning, and must not be forced to satisfy a guard written for another one.

So: `from_dict(raw, *, allow_empty: bool = False)`. Keyword-only, defaulted `False` -- **every existing caller keeps the guard byte-identically**, and there are five of them that must:

| Call site | Path | Guard must stay |
|---|---|---|
| `fields/loader.py::load` | file load (CLI `--fields`) | yes |
| `api/routes/upload.py:375` | the field_set upload path | yes |
| `api/routes/field_sets.py:39` | `POST /api/field-sets` | yes |
| `api/routes/confirm.py:69` | the client-drift check | yes |
| `learning/postgres_field_set_store.py:82` | stored-profile rehydrate | yes |
| `api/routes/schemas.py:45` | **`POST /api/schemas`** | **NO -- opts in** |

This is the opposite of weakening the guard: it is naming, in one place, the single entry point the guard was never about.

**No frontend change is in scope.** Verified during planning: `frontend/src/screens/Schemas.tsx:152` ALREADY calls `promoteSchema(name, { name: null, fields: [] })`, and `lib/api.ts::promoteSchema` already posts `{ name, field_set }`. The wire contract is already correct and already satisfiable -- the backend is simply rejecting it. `SchemaControls.tsx:97`'s promote-from-a-real-field-set path also keeps working unchanged (a non-empty `fields` list never touches the new branch).
