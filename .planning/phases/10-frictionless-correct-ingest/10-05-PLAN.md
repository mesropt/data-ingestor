<objective>
Put the escalation and the date question on the wire.

Three changes to the HTTP surface:
1. **The Schema is the target (INGEST-01/D-10-02).** `/api/upload` accepts `schema_name` and derives the field set from it. The `field_set` JSON form field stays supported (the CLI and every existing test use it) — this is additive, not a replacement.
2. **A 4th response arm (INGEST-04/D-10-07).** `kind: "date_question"` — surfaced when Python cannot determine a mapped date column's order and no declared format covers it. It rides the existing retained-upload-token registry, exactly as `structural_question` and `reconcile_question` already do.
3. **Escalation counts (INGEST-02).** The mapping response reports how many fields the Python crosswalk pass matched vs how many needed Claude — the one visible proof of the escalation order.

Purpose: `headers_only` restricts what CLAUDE sees, not what the SERVER reads (D-10-05) — but the toggle still governs what the *human reviewer* is shown. The wire layer is where that distinction becomes real: detection is unaffected, and the evidence values are redacted.
Output: an extended upload route, a new `/api/date-format/resolve` route, the wire models, and the retained-state they need.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/date-format/resolve` | An untrusted client answering a safety-critical question about how to interpret every date in a file |
| browser → `POST /api/upload` (`schema_name`) | An untrusted client naming which governed Schema to map against |
| server → browser (`date_question` response) | The `headers_only` privacy boundary: cell values must not cross when the toggle is on |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-21 | Tampering / Elevation of Privilege | `DateFormatChoiceIn` | critical | mitigate | A tampered client sending a fabricated `date_format` (or a `resolved: true` flag) to bypass the ambiguity gate and flip every date. The request model carries ONLY an `order` Literal — there is no format field to send. The server re-classifies the retained column and derives the strptime format itself, mirroring `service.confirm`'s "rebuild fresh, never trust the client's readiness claim" discipline. Pinned by a test that sends an extra `date_format` key and asserts it is dropped. |
| T-10-22 | Tampering | unanswered ambiguous columns | high | mitigate | An empty or partial `choices` list silently proceeding to a mapping with a guessed order. `UnresolvedDateColumnsError` → 422 naming each undecided column, BEFORE any assembly. Fail closed, mirroring `UnresolvedConflictsError`. |
| T-10-23 | Information Disclosure | `date_question` response under `headers_only` | high | mitigate | Cell values leaking to the browser through a NEW response arm that the existing `headers_only` tests do not cover. `DateFormatQuestionResponse.from_question(..., headers_only=True)` strips `example_values` to `[]` in the wire layer, in one place. Pinned by a test asserting no cell value appears anywhere in the serialized body. |
| T-10-24 | Tampering | retained `UploadEntry` state | medium | mitigate | A client re-sending a different table/proposal/field set at resolve time. Nothing in `DateFormatResolveRequest` carries them — the server re-finds the retained `table`/`proposal`/`field_set` by `upload_token` (the T-08-08 discipline). |
| T-10-25 | Information Disclosure | `schema_name` on upload | low | accept | A signed-out caller can map against any Schema by name. INGEST-06 makes sign-in a UI-level requirement (Plan 06); the governed MUTATIONS (confirm, edit, augment) remain server-gated as they are today. No new exposure is introduced by this plan. |
| T-10-SC | Tampering | npm/pip/cargo installs | high | mitigate | **This plan installs ZERO new packages.** No package-legitimacy checkpoint is required because no install task exists. |
