<objective>
Make removal a tombstone, not a DELETE (D-10-15), and give `SchemaStore` its first genuine UPDATE/remove methods. Backend persistence only — no service, no HTTP, no UI.

Purpose: a governed crosswalk that forgets who removed a field is not a governed artifact. Soft delete keeps the audit trail and, as a bonus, sidesteps the missing `ON DELETE CASCADE` on the alias→field foreign key (nothing is physically deleted, so the constraint is never exercised). The accepted cost — every read path must now filter tombstones — is paid down structurally in this plan by filtering inside the store's four queries, and paid down again by explicit tests in Plan 03 against each consuming path.
Output: an Alembic migration, four tombstone columns, two partial unique indexes, three new `SchemaStore` ABC methods with their Postgres implementations, and a test file that hammers every tombstone edge.
</objective>

    **1b. Make both UNIQUE constraints PARTIAL.** This is the load-bearing change and it is easy to miss:

    Today `AliasRow` has `UNIQUE(canonical_field_id, vendor, source_column)` and `add_alias` writes `ON CONFLICT DO NOTHING` against it. If a tombstoned alias row keeps occupying that unique key, then re-adding the same vendor/column pair after a removal hits the conflict, does nothing, and the alias is invisible **forever** — a silent, permanent data-loss bug that no "it compiles" check catches. Same hazard on `CanonicalFieldRow`'s `UNIQUE(schema_id, name)` and `_insert_missing_fields`.

    Replace both `UniqueConstraint` declarations with **partial unique Indexes** predicated on `removed_at IS NULL`:
      - `Index("uq_canonical_field_live", "schema_id", "name", unique=True, postgresql_where=text("removed_at IS NULL"))`
      - `Index("uq_alias_live", "canonical_field_id", "vendor", "source_column", unique=True, postgresql_where=text("removed_at IS NULL"))`

    A tombstoned row therefore no longer blocks a fresh insert. Re-adding a removed field/alias creates a NEW live row with its own fresh provenance — which is correct: it IS a new human decision, with a new actor and timestamp, while the tombstoned row survives as audit history. ALIAS-03's "first-seen provenance is never overwritten" still holds exactly: nothing is ever `DO UPDATE`-d.

    **1c. Write the Alembic migration** (`uv run alembic revision -m "soft delete canonical field and alias"`, then hand-write the body):
      - `op.add_column` × 4.
      - `op.drop_constraint` the two existing unique constraints (look up their real generated names — do not guess; `\d canonical_field` / `\d alias` against the dev DB, or read the initial migration).
      - `op.create_index(..., unique=True, postgresql_where=sa.text("removed_at IS NULL"))` × 2.
      - A working `downgrade()` that reverses all of it.
