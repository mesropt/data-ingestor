# Phase 10 — UI Design Contract

> Visual and interaction contract for collapsing Upload to three controls, merging Define Fields + Registry into one editable **Schemas** page, making sign-in mandatory app-wide, and adding the "ask the date order once per column" flow. Generated by gsd-ui-researcher from `10-CONTEXT.md` (D-10-01..14) and REQUIREMENTS.md (INGEST-01/02/04/05/06). **This is an EXTENSION, not a new design system** — every token, component primitive, icon, and font already shipped in `frontend/src/` (04-UI-SPEC.md, extended by 06-UI-SPEC.md) is binding and reused verbatim. No new hex value, type size, weight, or shadcn registry install is introduced anywhere in this document.

**A frontend already exists** with a working Upload → Review → Registry/Docs loop and a sign-in/sign-up/verify surface (Phase 6). This phase deletes one screen, renames and substantially grows another, shrinks a third, and adds one new inline question type.

## Discretion Calls (Claude's Discretion in `10-CONTEXT.md`, resolved here)

### 1. Schemas page layout: row expansion, not a side panel

**Decision: inline row-expansion (accordion), one row open at a time.** A canonical field's row renders **collapsed** by default — name, a `Label/mono` summary line (`type · unit · required · N aliases`), an edit-pencil icon, and a delete-trash icon. Clicking the pencil expands that row in place (any other open row collapses first) to reveal:
- the full constraints form, **reusing `FieldEditorRow`'s exact field layout** (Name, Description, Type, Unit, Min/Max when numeric, Date format when date, Allowed values chip-input, Required switch) — because `CanonicalField`'s constraints ARE `Field`'s constraints (D-10-11), the same component/grid applies verbatim;
- below it, a **"Vendor Aliases"** section: a read-only list of existing aliases (vendor, source column, provenance badge — reusing `RegistryTable`'s `AliasRow` styling) each with a trailing remove-icon, plus a small "add alias manually" inline form (Vendor + Source column inputs + "Add Alias" button);
- a "Save Field" / "Cancel" pair at the bottom of the expanded block.

**Why expansion over a side panel:** (a) it matches the requirement's own literal shape — "one table per Schema, one row per canonical field" (D-10-10) — a side panel would turn a one-row-per-field TABLE into a table-plus-drawer, two visual paradigms doing one job; (b) it needs zero new shadcn primitive (`Sheet`/`Drawer` isn't in the app today — see Registry Safety), keeping the phase inside the existing design system exactly as constrained; (c) `RegistryTable`'s current row-group layout (identity pane left, aliases pane right) already visually anticipates this — expansion just makes the existing read-only right pane editable and adds an editable left pane, rather than inventing a new interaction model; (d) a side panel implies "detail view of one field elsewhere," which reads as navigation — this is a same-page governance edit, and the builder's own words ("Пусть на странице Schemas можно будет редактировать key value") frame it as in-place editing of the row itself, not a drill-down.

### 2. The per-column date question: reuse `StructuralHintPanel`'s shape, as a new 4th response arm

**Decision:** introduce a 4th discriminated `kind: "date_question"` arm alongside `mapping` / `structural_question` / `reconcile_question`, surfacing **only the genuinely-ambiguous case** (D-10-07 — no reliable DD/MM-vs-MM/DD signal, no declared format to fall back on). It is checked server-side, in pure Python, **after** the Python→Claude mapping stage resolves which source column feeds each date-typed field, and **before** a final `mapping` response is returned — the same position in the escalation chain a structural hint or reconcile conflict already occupies. Multiple ambiguous columns are bundled into **one** `DateFormatQuestionPanel`, one sub-block per column, **one submit** for all of them at once — mirroring `ReconcilePanel`'s multi-conflict/single-submit shape (not `StructuralHintPanel`'s single-question shape, since there can genuinely be more than one ambiguous date column in one file). It renders inline below the dropzone in the **same** Upload flow, never a modal — identical placement rule to `StructuralHintPanel`/`ReconcilePanel`.

Per column, two selectable option buttons ("DD/MM/YYYY" / "MM/DD/YYYY") each show a computed preview from the column's first evidence value (e.g. `03/04/2025` → "3 April 2025" vs "March 4, 2025") so the choice is concrete, not abstract — mirrors the structural-hint's "click a row to choose" concreteness principle. **Under `headers_only`, the evidence values and previews are hidden** (generic option labels only, plus a row/ambiguity count) — exactly the same privacy rule `StructuralHintPanel` already enforces for its evidence grid (explicitly required by the phase brief), even though D-10-05 establishes the underlying *detection* itself is unaffected by the toggle — the toggle still governs what the *human reviewer* is shown, consistent with the existing UI idiom.

**The declared-format-contradiction case (D-10-06) does NOT use this new panel.** It is not "ask once per column" — it is a per-field validator objection like any other, so it reuses the **existing** amber `FieldRow` + `validator_note` mechanism verbatim (zero new UI): the field goes amber, the reasoning line explains the contradiction, and the human resolves it via the existing Accept/chip/dropdown controls (or fixes the declared format later on the Schemas page). This keeps one new UI surface (the genuinely-ambiguous case) rather than two, and reuses more of the existing gate for the contradiction case.

### 3. Sign-in is an app-wide gate, not a per-action mirror

**Decision:** with INGEST-06 removing the anonymous path entirely, the Schemas / Upload / Review tabs each render a shared `SignInRequiredGate` full-pane interstitial in place of their real content whenever `!signedIn` — replacing (for these three tabs) the previous per-action mirror pattern (Phase 6's tiered `ConfirmGate`/`SchemaControls`/`MapFileControls` auth mirrors), which existed precisely because those actions used to be reachable anonymously and only specific mutations were gated. **The Docs tab remains open signed-out** — it is pure informational how-to/glossary content with no governed action behind it, and a prospective user reading what the tool does before creating an account is a reasonable, deliberate exception, not an oversight. Tabs stay visible and clickable while signed out (for orientation); clicking between Schemas/Upload/Review while signed out shows the same interstitial each time — an intentional non-surprise, not a broken nav.

This **supersedes Phase 09's D-09-05** ("viewing the Registry is open, no sign-in wall"). Phase 10 reverses it: there is no anonymous path at all now, for any of Schemas/Upload/Review.

The existing tiered gates are **not deleted**, only narrowed in scope: once signed in, `ConfirmGate`'s existing verified/ready tiers (Phase 6) and the Schemas page's edit affordances (verified-only, per D-10-12) are unchanged. Signed-in-but-unverified can still browse Schemas/Upload/Review; only the governed *mutations* (confirm, edit a Schema's fields/aliases) stay verified-gated, exactly as today.

### 4. Deleted pages: what happens to a stale bookmark

Deleting Define Fields and renaming Registry→Schemas is a **design act**, not a silent code change. A user with `/define-fields` or `/registry` bookmarked, or mid-session on either tab when this phase ships, must land somewhere coherent, not a blank screen or a 404. The existing `tabFromPath()` allowlist fallback (documented in its own code as resolving "even a garbage path" to a valid `TAB_VALUES` member) already does exactly this with zero new code required: once `TAB_VALUES` no longer contains `"define-fields"`/`"registry"`, those paths simply fall through to the same default-tab fallback a typo'd path already gets today. This MUST be verified to still hold (a regression here would silently 404 or blank-page a returning user) — it is not a new mechanism to build, but an existing guarantee this phase must not break.

### 5. Quick task 260712-e0e is fully reverted, not extended

`FieldSetPicker`, its field-set auto-select (`pickDefaultTemplateId`/`readLastTemplateId`/`writeLastTemplateId`), and its disabled-submit hint (`submitBlockedReason`) are **deleted outright**. The Upload screen's new `SchemaPicker` (see Screens & States) is a fresh, simple, unauto-selecting `Select` — the user always picks explicitly from the (typically 4+, seeded) list of Schemas. No "last used" persistence, no auto-pick-if-only-one-exists logic is carried forward from e0e; if a future phase wants that convenience back, it is a new, deliberate decision against the new Schema-based picker, not an inherited behavior.

### 6. Review's `SchemaControls` shrinks to a vendor label only

Today, `Review.tsx` embeds a *second*, independent Schema selector (`SchemaControls`) purely to choose which Schema receives the confirmed mapping's aliases — separate from whatever field set the Upload screen mapped against. With Upload's Schema selection now identical to the mapping target (D-10-02), that second selector is redundant and confusing (it could disagree with the Schema the file was actually mapped against). **Decision:** Review no longer renders a Schema selector at all. The Schema name the upload was mapped against is threaded through from Upload (same mechanism `fieldSet` already uses) and shown **read-only**, mono-styled, next to the existing `upload {token} — {field set name}` line (e.g. `upload a1b2c3 — assay-potency`). Only the **Vendor (source label)** input survives from `SchemaControls`, unchanged in behavior, still defaulting to a sensible label and still threaded into `/api/confirm`'s `schema_name`/`vendor` fields (now `schema_name` is fixed, never re-chosen here). `SchemaControls`'s promote/download/import affordances move to the Schemas page (see Screens & States §1) since "promoting a field set" no longer makes sense once Schemas exist independently and don't originate from a separate field-set editor.

## Screens & States

### 1. Schemas (INGEST-05 — replaces Define Fields + Registry)

**Layout:** single-column, `max-w-5xl` (matches the old Registry width — this table needs room), centered.

**Toolbar (top):**
- Schema `Select` (existing schemas, from `GET /api/schemas`) — placeholder "Choose a Schema…" or, if none exist, "No schemas yet."

- "Download master map" (plain `<a download>`, unchanged from `SchemaControls`) and "Import master map" (file input, augment-only per D-07-04, unchanged from `SchemaControls`) — both moved here verbatim from Review/Registry, disabled/tooltipped exactly as `SchemaControls` already implements.

**Field list (below toolbar, once a Schema is selected):** one collapsed row per canonical field, rendered top-to-bottom in the Schema's own field order. Each collapsed row: field name (`Body 16/600`), `Label/mono` summary (`type · unit · required · N alias(es)`), a `Pencil` icon button (opens the row), a `Trash2` icon button (destructive, `AlertDialog` confirm per Copywriting Contract).

**Expanded row (accordion — only one open at a time, see Discretion §1):**
- The full constraints form, verbatim `FieldEditorRow` layout, pre-filled with the field's current values.
- "Vendor Aliases" section (`Heading 20/600`): existing aliases as read-only rows (vendor, source column, provenance badge — reusing `RegistryTable`'s `AliasRow` visual, adding a trailing `X` remove-icon per alias, destructive-confirmed).

- "Save Field" / "Cancel" button pair, bottom-right of the expanded block.

Adding a brand-new field to the selected Schema reuses the SAME expanded-row form, opened via a top-of-list "Add Field" `Button` (identical placement/behavior to `FieldSetToolbar`'s old "Add Field", now scoped per-Schema and hitting the new explicit edit endpoint instead of a local draft).

**States:**
- No schemas at all: `EmptyCard` per Copywriting (mirrors today's Registry `EmptyCard`).
- No Schema selected yet: `EmptyCard` ("Choose a Schema" — reused from today's Registry idle state).
- Loading a Schema's fields: 3 `Skeleton` rows (`h-20`), toolbar remains interactive.
- A selected Schema with zero fields: empty state per Copywriting + "Add Field" CTA.
- Field-cap warning: identical to old Define Fields — "Add Field" disabled with tooltip "Field sets are capped at 50 fields." once at `MAX_FIELDS`.
- Save/delete/add-alias/remove-alias error: inline destructive `Alert` above the affected row, consequence-first copy, nothing lost (the expanded form's in-progress edits are preserved on a failed save).
- Signed-in-but-unverified: every mutating control (Create Schema, Add Field, Save Field, delete field, Add Alias, remove alias, Import master map) is disabled with the existing `Tooltip` "Verify your email to…" pattern; viewing (selecting a Schema, expanding a row read-only) is unaffected by verification — only signed-in-at-all is required to reach this tab per the app-wide gate (Discretion §3).

### 5. Date Format Question Panel (NEW — INGEST-04, D-10-07)

See Discretion §2 for the full design rationale. Structural summary:

**Layout:** one `Card` (mirrors `ReconcilePanel`'s exact shape), rendered inline below `UploadDropzone`, replacing/alongside the other two question panels (never more than one showing at once — the escalation order guarantees at most one question kind is pending per upload attempt).

- `CardHeader`: `CalendarClock` icon + `CardTitle` "Confirm date order" (`text-heading`) + intro body line (per Copywriting Contract, pluralized on column count).
- `CardContent`: one bordered block per ambiguous column (`rounded-lg border border-border p-3`, mirrors `ReconcilePanel`'s per-conflict block), each containing:
  - the per-column reason line (`Label`, source column mono-styled);
  - two selectable option buttons side by side ("DD/MM/YYYY" / "MM/DD/YYYY"), each showing a computed preview under `!headersOnly`, or the generic headers-only note in place of both previews;
  - the selected option gets the existing accent border+fill treatment (same rule as a selected `ConfidenceChip`/alternative-chip).
- One "Use This Order and Continue" `Button` at the bottom, disabled while submitting (`Loader2` spinner, unchanged idiom), submitting ALL column answers in one request.
- The helper line (per Copywriting Contract) sits beneath the submit button, small `Label/muted` text — explains why this is asked only once.

## Layout & Responsive Behavior

- Schemas is single-column, `max-w-5xl`, centered — same width class as today's Registry (it holds a wide field+alias table, not a narrow form). It reflows naturally; no horizontal-scroll special-casing (that rule is specific to Review's two-pane region, unchanged).
- The Sign-In-Required interstitial is `max-w-[420px]`, matching Sign Up/Sign In/Verify Landing exactly, for the same "no layout jump between related auth-adjacent screens" reason established in `06-UI-SPEC.md`.
- `DateFormatQuestionPanel` and `ReconcilePanel`/`StructuralHintPanel` share the Upload screen's `max-w-[720px]` container — no new width class introduced.
- `AppShell`'s top bar geometry (h-16, `max-w-5xl`) is unchanged; four tabs (Schemas/Upload/Review/Docs) fit the existing `TabsList` with room to spare (one fewer than today's five).
- `ConfirmGate`'s 64px sticky-footer height is unchanged; nothing added to Review's header block (Schema name, vendor input, escalation summary) affects the footer's own layout math, since all of it sits above the (unchanged-height) `ReviewTable` region.
