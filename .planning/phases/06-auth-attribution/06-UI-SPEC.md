# Phase 6 — UI Design Contract

> Visual and interaction contract for the sign-up / sign-in / verify / signed-in-attribution surfaces added on top of the already-shipped v1.0 frontend. Generated by gsd-ui-researcher from `06-CONTEXT.md` (D-06-01..07) in **autonomous overnight mode** — no user questions were asked; every value below either reuses a token already locked in `04-UI-SPEC.md` / `frontend/src/index.css`, or is a direct, unambiguous derivation of it. This is an EXTENSION, not a new design system: the shadcn primitives, Tailwind tokens, dark-theme mechanism, and screen-composition idiom already shipped in `frontend/src/` are binding and are NOT re-specified here except by reference.

**A frontend already exists.** No new tool, preset, icon library, or font is introduced. All auth screens/components use the same `frontend/src/components/ui/*` primitives (`button`, `input`, `label`, `card`, `alert`, `badge`, `separator`, `tabs`, `tooltip`, `sonner`) already installed and already tokenized to the Phase 4 palette.

## Color

**Reuse verbatim — no new hex values, no new semantic role.** All auth surfaces are built from the existing tokens in `frontend/src/index.css`:

| Role | Token (light / dark) | Usage in this phase |
|------|------------------------|----------------------|
| Dominant (60%) | `--background` (`#F7F9F8` / `#0B1414`) | Sign Up / Sign In / Verify screen canvas |
| Secondary (30%) | `--card` (`#FFFFFF` / `#16201F`) | The auth form `Card`; `AppShell` top bar (`--secondary`) unchanged |
| Accent (10%) | `--primary` (`#0F766E` / `#2DD4BF`) | Primary CTA ("Create Account", "Sign In"), focus rings on email/password inputs, the "Sign in" text link inside the disabled-Confirm tooltip/redirect, the verified-state `MailCheck` icon accent |
| Success | `--success` (`#16A34A` / `#4ADE80`) | "Email Verified" landing state icon + accent bar — reuses the exact same green already reserved for a *clear field row* on Review; verification success is a parallel "this is now correct/complete" signal, never the accent teal (per 04-UI-SPEC's hard rule that success and accent must stay visually distinct) |
| Uncertain / amber | `--uncertain` / `--uncertain-bg` / `--uncertain-foreground` | The "check your server console" notice card after Sign Up — this is a **transitional, not-yet-complete** state (parallel to a `needs_confirmation` field), so it reuses the amber wash + border, NOT a plain info-blue (there is no info-blue token — do not invent one) |
| Destructive | `--destructive` / `--destructive-bg` / `--destructive-text` | Invalid credentials / sign-up failure inline `Alert` only |
| Border / divider | `--border` | Card border, input border, `Separator` between password field and Google button |
| Text primary/secondary/disabled | `--foreground` / `--muted-foreground` / (input `disabled:opacity-50`) | Standard text hierarchy, unchanged |

**Accent reserved for (this phase, additive to the existing reserved list — nothing removed from it):** the Sign Up/Sign In primary CTA buttons, input focus rings, the "Sign in" link/CTA that the disabled Confirm gate routes to, and the signed-in `UserRound` icon in the `AppShell` (a quiet accent-tinted icon, not a colored badge — this is presence/attribution, not a call to action). **Never** used for the amber transitional-notice card or the destructive credential-error alert — those keep their own reserved colors exactly as Phase 4 declared.

Both themes (light-primary, dark-secondary via `[data-theme="dark"]`) are already token-complete; no auth screen introduces a theme-conditional value that isn't already a CSS custom property.

## Screens & States

### 1. Sign Up (new screen)

**Layout:** identical centered-form idiom to Upload/DefineFields — single `Card`, `max-w-[420px]` (narrower than the 720px form screens; this is a two-field form, not a multi-control panel), centered on the canvas with `xl` (32px) top padding.

**Structure top to bottom inside the `Card`:**
1. `CardTitle` — "Sign Up" (Display 28/600, matching the screen-title convention used by `<h1 className="text-display">` on Upload/DefineFields — reuse that exact class, do not introduce a `CardTitle`-driven size).
2. Email `Input` + `Label` ("Email"), `type="email"`, `autoComplete="email"`.
3. Password `Input` + `Label` ("Password"), `type="password"`, `autoComplete="new-password"`, helper text below in Body 16/400 muted: "At least 8 characters."
4. Primary CTA — full-width `Button` (`variant="default"`), "Create Account".
5. `Separator` + "or" label, **rendered only when** `/api/auth/config` reports the Google flag ON.
6. Google button (**conditional — see Component Inventory**), full-width, `variant="outline"`, `Chrome` icon + "Continue with Google".
7. Cross-link, Body 16/400: "Already have an account? **Sign in**" (the bold portion is a `variant="link"` `Button` or plain `<a>` styled as a link — reuse `Button` `link` variant token, `text-primary`).

**States:**
- Default: as above, CTA enabled once both fields are non-empty (client-side convenience only — server is the actual validator, per P1).
- Submitting: CTA shows the same `Loader2` spinner idiom already used on `ConfirmGate`/`FieldSetToolbar` ("Creating…" label), all inputs disabled.
- Success: the `Card` content is REPLACED (not stacked below) by the "Check your server console" notice — amber-toned `Alert` (`--uncertain-bg`/`--uncertain`/`--uncertain-foreground`), `Mail` icon, heading + body per Copywriting Contract, "Sign in now" secondary `Button` (`variant="outline"`).
- Error: inline destructive `Alert` above the form fields (same position/pattern as `Upload.tsx`'s `templatesError` alert), form state preserved, offending field gets `aria-invalid` (already styled red-ring by the shared `Input`/`Button` classes — no new class needed).

### 2. Sign In (new screen)

**Layout:** same `Card`/`max-w-[420px]` pattern as Sign Up, for visual symmetry (a user bouncing between the two via the cross-link should see no layout jump).

**Structure:** Display title "Sign In" → Email `Input` → Password `Input` (no helper text needed here, min-length isn't relevant on sign-in) → primary CTA "Sign In" → conditional Google divider+button (identical rule as Sign Up) → cross-link "Don't have an account? **Sign up**".

**States:**
- Default / Submitting: same idiom as Sign Up (spinner + "Signing in…" label, disabled inputs).
- Error — bad credentials: destructive inline `Alert`, copy per Copywriting Contract. Password field is cleared on this specific error (do not force the user to re-see their wrong password — email stays for convenience).
- **Redirected-here-from-Confirm case:** when Sign In is reached via the `ConfirmGate`'s "Sign In to Confirm" affordance (not a fresh nav), render one extra `Body` line above the form, muted: "Sign in to confirm your mapping." This is the ONLY contextual variation between a standalone visit and a redirected visit — no separate route/screen is needed, just one conditional line driven by a `returnTo` param/state the auth store already needs to carry.
- Unverified-blocked-governed-action case (user signs in fine, but then hits a governed action gated on verification): this is NOT a Sign In screen state — see ConfirmGate's own "signed-in but unverified" state below. Sign In itself never blocks on verification per D-06-04.

### 3. Email Verification Landing (new screen/route, reached only via the console-printed link)

**Layout:** same centered `Card` pattern, `max-w-[420px]`, but content is a single centered result state — no form.

**Structure:** centered icon (`MailCheck` success-green, or a muted `Mail` for the expired case) → Display heading → Body copy → single CTA `Button` ("Sign In").

**States:**
- Verified (success): `MailCheck` icon in `--success` color, heading "Email Verified", body + CTA per Copywriting Contract. This is the SAME success-green token as a clear `FieldRow` on Review — reinforces "this is now resolved/correct," not a celebratory/marketing moment (governance framing: calm, not confetti).
- Expired/invalid token: muted `Mail` icon (`text-muted-foreground`, not destructive-red — an expired link is an expected lifecycle state, not an error the user caused), heading "This link has expired", body + CTA per Copywriting Contract.
- Loading (token verification call in flight): a single centered `Loader2` spinner, no layout — this call is near-instant (a local DB lookup), so no skeleton is needed, just the spinner to avoid a flash of empty content.

### 4. AppShell — signed-in identity + sign-out (extends existing `AppShell.tsx`)

**Placement:** trailing edge of the top bar, immediately after `ThemeToggle` (rightmost element) — mirrors the existing `justify-between` layout (`wordmark ... tabs ... ThemeToggle`) by appending one more trailing group, NOT restructuring the bar.

**Signed-in state:** a compact inline group — `UserRound` icon (`size-4`, `text-muted-foreground`) + email in `.text-mono-label` + an icon-only `LogOut` `Button` (`variant="ghost"`, `size="icon"`), gap `xs` (4px) between icon and email, `sm` (8px) before the Sign Out button. The email is NOT a dropdown/menu trigger — clicking it does nothing (per `06-CONTEXT.md`: "quietly visible... not a heavy account-management surface"). Only the `LogOut` button is interactive.

**Signed-out state:** a single "Sign In" `Button` (`variant="outline"`, `size="sm"`) in the same trailing slot — never a blank gap where the identity group would otherwise sit, so the bar's width/rhythm doesn't shift between signed-in and signed-out.

**Loading (session check in flight, e.g. on page load before `/api/auth/config`+session probe resolves):** render the signed-out "Sign In" button's slot as a low-opacity placeholder (`opacity-50 pointer-events-none`, no skeleton bar needed — this resolves in well under a second against a local SQLite session check) rather than nothing, to avoid a layout shift once the real state arrives.

### 5. ConfirmGate — signed-in-required mirror (extends existing `ConfirmGate.tsx`, does NOT replace its `is_ready` logic)

This is the most consequential state addition in this phase: the auth gate must **compose with**, not override, the existing readiness gate. `ConfirmGate` already disables on `!ready`; this phase adds a **second, independent disable reason** — being signed out or unverified — and the two must never be conflated in copy (a curator resolving amber fields while signed out needs to see BOTH "resolve fields" and "sign in" as distinct blockers, not one confusing merged tooltip).

**Priority order when the button is disabled (mirrors server-side check order — auth gate runs first per `require_user`, per D-06-06):**
1. **Signed out** → button label changes from "Confirm & Save Mapping" to **"Sign In to Confirm"**, `ShieldAlert` icon prefix, `Tooltip` copy "Sign in to confirm this mapping." Clicking it (it's not fully inert — see below) navigates to Sign In carrying a `returnTo` back to this Review screen/state. This is a rare case where a "disabled-looking" button is actually clickable (to preserve the redirect affordance) — style it as `variant="outline"` (not the greyed-out `disabled` treatment) so it doesn't read as inert, since it IS actionable, just not in the way the label "Confirm & Save Mapping" implied.
2. **Signed in, not yet verified** → label stays "Confirm & Save Mapping" but is truly `disabled` (matches existing disabled visual treatment), `Tooltip` copy "Verify your email to confirm this mapping."
3. **Signed in, verified, but `!ready`** (existing Phase 4 behavior, unchanged) → existing "Resolve {n} more uncertain field(s) before confirming." tooltip, existing disabled treatment.
4. **Signed in, verified, `ready`** → existing enabled "Confirm & Save Mapping" behavior, unchanged. On success, the confirm success toast (existing copy, unchanged) — no new copy needed since D-06-06's attribution stamping is a server-side/data concern, not a UI-visible change to the success state.

**Never** show more than one of these four states' copy at once — they are mutually exclusive priority tiers, not a stacked checklist.

## Layout & Responsive Behavior

- Sign Up / Sign In / Verify Landing are all single-column, centered, `max-w-[420px]` `Card`s — narrower than the existing 720px (Upload) / 840px (DefineFields) form screens, appropriate for a two-field form, and they reflow naturally at any width exactly like the other centered screens (no special-casing, no horizontal-scroll concerns — this rule is specific to the Review screen's two-pane region and does not apply here).
- The `AppShell` top bar's new trailing group (`SignedInIndicator`) must not cause the bar to wrap at the existing `max-w-5xl` container width used across all viewport sizes the demo targets (laptop, desktop) — if email length threatens overflow at narrow widths, truncate the email with `text-ellipsis`/`max-w-[160px]` rather than wrapping the top bar to a second line (the bar's single-row height is load-bearing for the existing `ConfirmGate` sticky-footer math in `04-UI-SPEC.md`'s Layout section).
- `ConfirmGate`'s height (64px, `3xl` token) is unchanged by this phase — none of the new label/icon combinations (`ShieldAlert` + "Sign In to Confirm") require extra vertical space; they fit the same single-line button treatment as the existing "Confirm & Save Mapping" label.
