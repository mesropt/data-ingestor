<objective>
Deliver the learning loop's money-shot: a curator confirms a fully-clear mapping once, saves it as a local SQLite profile, and every later file with the same column signature auto-maps at confidence 1.0 without a single Claude call. Build the order-independent column signature (LEARN-01), the pure-domain profile model + repository seam (LEARN-02/05), the SQLite store behind that seam (D-01), and the auto-apply reconstruction that safely resolves stored columns against a normalisation-tolerant signature match (LEARN-03/04/06) — the P1 correctness hazard this phase most has to get right.

Purpose: This is the project's differentiator and the demo's central moment — "the second file from the same lab is zero-yellow, auto-mapped, no data left the machine." It is also a privacy control (P2): a known format needs zero Anthropic calls.

Output: `src/assayingest/learning/` package (signature, profile, store ABC, sqlite_store, reconstruct), `cli.py` wired for `--save-profile` / `--profiles-db` / auto-apply, `.gitignore` covering the store, and an offline money-shot integration test.
</objective>

## Phase Goal (user story)

**As a** data curator who reformats a given lab's CRO files repeatedly, **I want to** save a mapping I have confirmed once and have the tool auto-apply it to the next same-format file with no AI call, **so that** repeat files become a zero-click, zero-data-leaving-the-machine review instead of manual re-mapping.

After each task a curator can do something new: (1) the tool can fingerprint a file's columns stably; (2) a confirmed mapping survives to disk and comes back; (3) the second same-signature file auto-maps end-to-end with no Claude call.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| uploaded file → signature/store | Header strings are untrusted file content; they flow into signature hashing and into SQL parameters. |
| stored profile → auto-applied mapping | A wrong-file match would silently corrupt exported data (P1's core fear). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | SqliteProfileStore queries | high | mitigate | Parameterised `?` placeholders in every sqlite3 query; a header string is never f-string-formatted into SQL (ASVS V5). |
| T-03-02 | Tampering / Repudiation | auto-apply reconstruction | high | mitigate | Exact-signature-only match (D-02/D-05, never relaxed) PLUS normalised-lookup reconstruction (Pattern 4) so a genuine match never silently drops a column; auto-applied provenance is printed (D-08) and recorded later in the export manifest. |
| T-03-03 | Information Disclosure | learning loop as privacy control | medium | mitigate | A profile hit issues zero Claude calls and constructs no client — no file data leaves the machine on the repeat path (P2, D-10 principle). |
| T-03-04 | Tampering | `--profiles-db` path argument | low | accept | Local trusted CLI operator in v1; absolute-path/traversal hardening is deferred to the Phase 4 server surface (RESEARCH Security Domain). |
| T-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages this phase (stdlib sqlite3/json/hashlib/unicodedata/uuid) — RESEARCH Package Legitimacy Audit confirms nothing to install; nothing to slopcheck. |
</threat_model>
